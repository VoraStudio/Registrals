    Rutes: webhooks i API¶

    Mapa dels endpoints de webhooks (notificacions push de proveïdors externs) i de la petita API interna (JSON sense plantilla). Totes les rutes són PUBLIC_ACCESS al tallafoc: la seva seguretat rau en la validació de firma (Stripe / Namirial) i en el fet que no exposen cap operació d'escriptura sensible.

    Font: bin/console debug:router (nucli del 17/11/2026). 4 rutes en aquest fitxer.

    Webhook de Stripe (Webhook\StripeWebhookController)¶

    Ruta Path Mètode Descripció
    app_webhook_stripe /webhook/stripe POST Rep les notificacions de Stripe (checkout.session.completed, invoice.paid, customer.subscription.updated/deleted, payment_intent.payment_failed…).

    Comportament:

    1. Validació de firma: el controlador comprova el capçal Stripe-Signature contra STRIPE_WEBHOOK_SECRET (timestamp + hash del payload + signatura, amb tolerància de reenviament). Si la firma no és vàlida, respon amb 400.
    2. Idempotència: cada event es processa només un cop (deduplicació per event.id); si l'event ja s'ha processat, es torna 200 sense efectes.
    3. Doble capa de seguretat: el webhook és la font de veritat per a l'activació de la subscripció; el flux de pagament del front (ruta app_payment_success) només mostra l'estat i mai activa el pla per si sol. La comanda app:stripe:sync-sessions reconcilia les transaccions pendents consultant directament l'API de Stripe (contingent per a webhooks perduts).
    4. Auditoria: cada event processat registreja PAYMENT_COMPLETED, SUBSCRIPTION_STARTED, SUBSCRIPTION_CANCELLED o PAYMENT_FAILED a registrals_audit.

    El monogràfic complet de la integració (billing, checkout, webhooks, idempotència i customer portal) és a sdd/06a-stripe.

    Webhook de Namirial OnBoarding (Webhook\NamirialWebhookController)¶

    Ruta Path Mètode Descripció
    app_webhook_namirial_onboarding /webhook/namirial/onboarding POST Rep el veredicte de la verificació d'identitat (eIDV) de Namirial OnBoarding API v2.

    Comportament:

    1. Validació de firma: el controlador comprova el secret de webhook (NAMIRIAL_ONBOARDING_WEBHOOK_SECRET) contra el capçal de signatura del proveïdor. Si el secret no està configurat o la firma no és vàlida, respon amb 400.
    2. Actualització d'estat: actualitza el KycSession associat (approved / rejected / pending) i el camp kycStatus de l'usuari.
    3. Auditoria: registreja KYC_APPROVED o KYC_REJECTED a registrals_audit.

    El monogràfic de la integració eIDV és a sdd/06b-signaturit (Namirial OnBoarding) i la verificació la fa el controlador KycController (init / callback / sync).

    API interna de seguiment (FeatureTrackerController)¶

    Ruta Path Mètode Descripció
    api_track_feature_interest /api/track/feature-interest POST Registra l'interès de l'usuari en una funcionalitat (telemetria d'ús).
    • Payload esperat: { "feature": "<feature_key>", "userId": "<uuid|null>" }.
    • Resposta: 204 No Content (sense cos).
    • Ús: el front crida aquesta ruta quan l'usuari fa clic en un CTA de funcionalitat (ex. "Vull aquesta funció"); s'emmagatzema a la taula feature_interest per a la prioritització del roadmap.
    • Privadesa: no s'envien dades personals identificatives; només el feature i (opcionalment) l'ID de sessió.

    API de traducció del blog (BlogController::translate)¶

    Ruta Path Mètode Descripció
    app_blog_translate /api/blog/translate POST Tradueix prèviament un article del blog a ES/EN (memòria cau per hash SHA-256).
    • Payload esperat: { "slug": "<article_slug>", "lang": "es|en" }.
    • Resposta: 200 amb { "translated": "<markdown traduir>" } o 204 si ja està a la memòria cau.
    • Memòria cau: el hash SHA-256 del contingut original + idioma fa de clau; si canvia l'article, es tradueix de nou. La comanda app:blog:pretranslate precarrega la memòria cau per a tots els articles publicats.

    Regles transversals¶

    1. CsRF exempt: els webhooks no inclouen token CSRF (no són peticions d'usuari); la seva seguretat rau en la firma. Assegura't de no afegir CSRF a aquests endpoints (no ho fa el tallafoc per defecte).
    2. Idempotència obligatòria: qualsevol webhook ha de ser idempotent (l'event es pot rebre més d'una vegada).
    3. Resposta ràpida: el controlador ha de respondre 2xx ràpidament; el processament pesat es delega a un servei o a una cua (Messenger) per no bloquejar el proveïdor.
    4. Monitorització: els webhooks perduts es poden detectar amb la comanda app:stripe:sync-sessions (Stripe) o amb la sincronització manual de Namirial (ruta app_kyc_sync).
    5. Aïllament: aquests endpoints no han d'estar darrere de cap autenticació d'usuari; són fonts de veritat de proveïdors externs.
